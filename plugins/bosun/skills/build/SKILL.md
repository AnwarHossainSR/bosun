# bosun build

Arguments: $ARGUMENTS

TB = `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/taskboard.py"` (`python` if `python3` is missing). The board (tasks.json) is the source of truth and **you are its only writer**; subagents never edit it. Prefer one TB call with several ids. Edge cases (shared mode, conflicts, resume, review policies, agent teams): [reference/execution.md](reference/execution.md), read the section you need.

**Style:** `output_style` in `.bosun/config.json` (default `caveman`): your prose and agent prompts terse, no filler; code, commands, paths, errors, numbers and quotes exact; keep logic words (because, so, but, not, only, can, may, must); full sentences for warnings, destructive steps, ordered steps, questions, requests to confirm and statements of uncertainty; never drop a fact or an uncertainty label. Commits, PR text, docs and specs: normal prose. `normal` turns it off.

**Your context lasts the whole build; keep it small.** Agents read their own briefs. The SubagentStop hook saves each bosun agent's final message to the plan's results folder, `.bosun/plans/<name>/results/<time>-<agent>-<task>-<id>.md` (agents name the board in their result block; messages without one go to `.bosun/results/`), so never copy result blocks into files. After the first agent finishes, check that the hooks ran: `.bosun/activity.jsonl` has its start and stop, and `ls -t .bosun/plans/<name>/results | head -3` shows its file. If not (no `python3`, an older Claude Code), put the project commands in every prompt and save result blocks and reviewers' verdicts to `.bosun/plans/<name>/reports/<ID>.md` yourself for the rest of the build; always do both for agents from outside bosun. Commands with long output (install, tests, lint, typecheck, build) go to a log you tail: `set -o pipefail; log=$(mktemp); echo "log: $log"; <cmd> >"$log" 2>&1; code=$?; tail -n 40 "$log"; echo "exit $code"; (exit $code)`; read more of that log only on failure. Read in full any path list you compare or act on (`git status --porcelain`, `git diff --name-only`, `git worktree list`).

**OpenSpec plans** are boards with `meta.openspec_change`; the change in `<openspec_dir>/changes/<id>/` is the contract. `<openspec_dir>` = `planning.openspec_dir` in `.bosun/config.json` (default `openspec`), the one setting the task board, the guard and these steps share; `TB status <board> --json` reports it resolved as `openspec.base`, and `TB brief` prints the change's absolute path. Briefs quote the requirements each task implements, `TB set --status done` ticks tasks.md, and only the architect edits the change. Run every `openspec` command from the OpenSpec directory's parent (repository root for `openspec`, `.bosun/` for `.bosun/openspec`): the CLI uses the nearest `openspec/` folder, so from elsewhere it can act on the wrong specs.

**Local OpenSpec directory:** one git ignores (`git check-ignore -q <openspec_dir>/changes` succeeds), such as `.bosun/openspec` beside a project's own OpenSpec. Its files never go into git: follow the *local* notes, which skip those git steps. Worktrees don't contain it; agents read the change from the main checkout via the absolute paths in `TB brief`.

**Tokens:** before anything else, run `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/usage.py" start` and note the `mark:` it prints. Its context above about 100k: tell the user once that every turn of the build re-reads it, so a fresh session (`/clear`; the board is on disk) is cheaper, then continue unless they stop you. At the end, run it with `report --since <mark> --agents 5` and end step 7's message with its lines as printed, never in a file you write or text you post. If the script fails, say so in one line.

## 0. Preflight (stop and ask about anything red)

1. **Board:** the argument (change id, slug, directory or path), else `TB latest`. A change id with a change directory (`<openspec_dir>/changes/<id>/`) but no board yet: run the `bosun:plan` skill with that id first (it adds only the board, and asks for approval), then continue here. `TB validate <board>`; OpenSpec plan: also `TB spec-check <board>` and, with the CLI (from the OpenSpec directory's parent), `OPENSPEC_TELEMETRY=0 openspec validate <id> --strict --no-interactive`. Errors mean stop.
2. **Settings:** `.bosun/config.json`; defaults when absent: `build.max_parallel` 4, `isolation` worktree, `review` task, `security_review` sensitive, `max_attempts` 2, `merge` merge. Flags override. Note `commands` (install, test, lint, typecheck, build).
   **Route:** `TB route <board> --json` (pass `--only` on): `solo`, one implementer for the tasks in `order`, then one review and one merge; or `crew`, parallel agents (`reasons` says why). `--crew` forces the crew, `--solo` solo when `solo_ok` is true (otherwise say why and use the crew). Solo needs worktree mode; shared mode uses the crew. Resuming with tasks `in_progress` or `review`: the route stays `meta.route` (unset: crew) whatever the flags; tasks in review (`in_review`) are left out of `order`, because their gates come first (step 4). `stuck` or `none`: still do steps 3 and 4, then section 3 or 4.
3. **Git** (worktree mode):
   - Clean working tree apart from ignored files, `.bosun/` and (OpenSpec plan) the uncommitted plan files: the change directory, plus `<openspec_dir>/config.yaml` if the plan created it. Otherwise ask the user to commit or stash first; never stash for them. One exception, an unfinished merge (`git rev-parse -q --verify MERGE_HEAD` succeeds, or after a squash the file at `git rev-parse --git-path SQUASH_MSG` exists): its staged and conflicted paths (`git diff --name-only --diff-filter=U`) are step 4's. Don't ask to commit or stash them (committing skips the integration check, stashing drops the merge, and with conflicts git refuses both). Anything else in the tree still counts.
   - Work branch: `meta.work_branch` set and not current (`git branch --show-current`): switch to it. During an unfinished merge never switch or check out a branch and never run `git merge --quit` (`git checkout` of the current branch silently drops the merge state); HEAD not the work branch then: stop and ask. No work branch yet: on the default branch create `bosun/<plan-name>`, on another branch use it, and record it once: `TB meta <board> --set work_branch=<b> --set base_branch=<default> --set base_commit=<sha> --set isolation=<mode> --set max_parallel=<N>`. On resume never overwrite `base_commit`: it bounds the final review.
   - OpenSpec plan whose `<openspec_dir>` is inside `.bosun/` but not git-ignored (`git check-ignore -q <openspec_dir>/changes` fails): stop and ask; it was meant to be local, and without an ignore rule the steps below would commit it.
   - OpenSpec plan with uncommitted plan files (*local: skip*): commit them on the work branch now (`git add -- <those paths>`, then `git commit -m "docs(spec): propose <id>"` in the repository's commit style). Worktrees hold only committed files, and implementers read the specs there.
   - Worktree base: subagent worktrees must branch from the current HEAD, not the default branch, or tasks miss the dependencies merged before them. Check only that setting, never the rest of those files: `grep -o '"baseRef" *: *"[^"]*"' .claude/settings.local.json .claude/settings.json ~/.claude/settings.json 2>/dev/null`. Not `"head"`: explain, and offer to add it as `/bosun:setup` does and restart the session, or to continue in shared mode.
   - Not a git repository: shared mode.
4. **Resume** (`--resume`, tasks already `in_progress` or `review`, or an unfinished merge from step 3): agents from the earlier session are gone. Read the reference, section "Resume", and decide now for each task and the merge. After step 5's go-ahead, settle an unfinished merge first, before any other resume action (gates, commits, `TB sync`, dispatch); a merge left to the user: start nothing until it's settled (`git rev-parse -q --verify MERGE_HEAD` fails, `SQUASH_MSG` is gone, `git diff --cached --quiet` passes). Then reset tasks with no work (`TB set <board> <ids> --status pending --note "reset on resume"`; a solo run's tasks it never reached stay `in_progress`: reference), and for an OpenSpec plan whose tasks.md `TB status` reports out of sync, run `TB sync <board>` and commit tasks.md (*local: skip the commit*).
5. **Confirm:** tasks remaining, resume decisions (including an unfinished merge, worktrees no task claimed, uncommitted paths outside a task), the route (solo: its order; crew: the `TB waves <board> --parallel <N>` summary and parallelism), isolation, review policy, work branch. Get a go-ahead before starting any agent unless the user already approved this build; an unfinished merge always needs one. `--dry-run`: also print the first prompt (crew: the first wave's) and `TB brief` for one of its tasks, then stop. Otherwise record the route: `TB meta <board> --set route=<solo|crew>` (briefs and the monitor read it).

## 1. Run the tasks

**Progress,** as OpenSpec's apply shows it: when tasks start, a line each, `▶ <ID> <title>` (solo: the run's list); when one is recorded done (section 2, step 8, and report tasks), `✓ <ID> <title> · <n>/<m>` with the count `TB set` printed (`3/7 tasks finished`).

**Solo route** (worktree mode): no scheduling; one implementer works through `order`.

1. `TB set <board> <ids in order> --status in_progress --assignee bosun:implementer`, then one Agent call: `bosun:implementer`, `isolation: "worktree"`, `name` `solo` (continuations `solo-2`, `solo-3`), `description` "<n> tasks solo", and this prompt:

   ```
   Tasks <ID>, <ID>, ... of bosun plan "<plan title>", solo: one at a time, in this order. Before each, read its brief: <TB> brief <absolute board path> <ID>
   Mode: worktree: your own git worktree on your own branch, created from the work branch "<work_branch>". Commit each task on its own there. Never push.
   Main checkout (read-only reference): <absolute path>
   <no docs task in the plan: last, update the docs the change affects (README, CHANGELOG if the project keeps one) in a `docs: <summary>` commit>
   <continuation only: First run `git merge <branch>`: it holds tasks <ids>, done<, and `wip(<ID>)` work to finish first>.>
   ```
2. **Result:** `tasks` gives each task's status and commit (`wip(<ID>)` commits are unfinished work); collect `spec_gaps` as section 2, step 1 says.
   - `needs_input`: ask the user (an answer that changes the spec: section 3 first), then SendMessage (`to` = its name) the answer.
   - Tasks it didn't reach because it stopped to keep its context fresh: a continuation, a new solo implementer for them with the continuation line (not SendMessage: its context is full).
   - A task `partial`, `failed` or `blocked`, no result block, or an agent that can't be resumed: the result's `tasks` (else the branch's `<type>(<ID>): ...` commits, never `wip`) show what's done, and section 3 handles the rest; a retry there is a continuation. A task left blocked: `TB route <board> --json` again, and continue with the tasks in its `order` that aren't done; those in `waiting` wait for the user.
   - Tasks it never reached stay `in_progress` (no `TB set`), so a continuation doesn't count an attempt for them.
3. **Review and merge once,** when every task of the run is done, skipped, blocked or waiting on one: section 2 from step 2, where `<ID>` is every task reported `done` and the task branch is the run's latest branch (if `wip` commits follow the last done task's commit: `git branch <branch>-done <that commit>`, and use that). The differences:
   - Gate: it is also the final review, so whatever the review policy its lenses are correctness and tests, `spec` for an OpenSpec plan and `design` above about 300 changed lines (step 3's size and security-reviewer rules apply).
   - Fix rounds: two for the run, and a red integration check counts as one (undo the merge, never send the run's tasks back to pending). Each re-runs the reviewers that blocked, plus the security-reviewer if the gate had one. Still blocking after two: the tasks the open findings concern go to section 3 as blocked, and nothing merges until the user decides.
   - Integration check: the full checks.
   - Record: step 8 with every id and the commit message `bosun(<ids, comma-separated>): <plan title>`; then `TB set <board> <ID> --summary "<its tasks summary>"` per task.
   - Clean up: every worktree and branch of the run (each continuation's supersedes the earlier ones).
4. **Then:** tasks pending again or added meanwhile (follow-ups via `TB add`): `TB route` for them, `TB meta <board> --set route=<route>`, and run them on that route. With `--only`, pass it on, adding the ids of tasks added to finish listed work (a split, a fix for a critical or high finding); other unlisted tasks, medium follow-ups included, wait for a later build, as on the crew route. Section 4 starts only when nothing is pending (with `--only`: no listed task is).

**Crew route** (rolling pool): read `${CLAUDE_PLUGIN_ROOT}/skills/build/reference/crew.md` and follow it until nothing is pending or in flight.

## 2. Per-task pipeline

1. **Result:** `done` continues. `partial`, `failed`, `blocked`, `needs_input` or no result block: section 3. Collect `spec_gaps` for the final report; a gap that blocks correctness goes to the user before more dependent tasks start.
2. **Spot-check** (code tasks, worktree mode): `git log --oneline <work_branch>..<task_branch>` shows its commits; `git diff --stat <work_branch>...<task_branch>` touches only expected files (never the OpenSpec directory, nor a project's own `openspec/`). List uncommitted paths with `git -C <worktree> status --porcelain --untracked-files=all`; those that belong to the task: commit them there with path-limited commands (`git -C <worktree> add -- <paths>`, then `git -C <worktree> commit -m "<type>(<ID>): <summary>" -- <paths>`), then repeat the `--stat` check; leave other uncommitted paths alone and note them. Out-of-scope files: accept with a note, or send the task back. Then `TB set <board> <ID> --status review --branch <task_branch> --worktree <path>`.
3. **Gate** (review policy `task`; `batch` and `final`: reference). Lenses: `correctness`; `spec` for a task with `spec_refs`; `tests` when its risk is high. A diff under about 400 changed lines (`git diff --shortstat <work_branch>...<task_branch>`; shared mode: `git diff --shortstat -- <task files>` plus the lines of its untracked files) gets one `bosun:code-reviewer` for all its lenses, a larger one a reviewer per lens. In the same message add `bosun:security-reviewer` in `diff` mode when the task is `security_sensitive`, `security_review` is `always`, or (policy `sensitive`) the diff touches auth, sessions, crypto, input parsing, queries, file or network I/O, permissions, secrets or config, or dependencies. Size and the reviewers' diff commands leave out lockfiles and generated files (`linguist-generated`) with these pathspecs, last and after `--`: `':(exclude,glob,top)**/*.lock' ':(exclude,glob,top)**/*-lock.yaml' ':(exclude,glob,top)**/package-lock.json' ':(exclude,glob,top)**/npm-shrinkwrap.json' ':(exclude,glob,top)**/bun.lockb' ':(exclude,glob,top)**/go.sum' ':(exclude,top,attr:linguist-generated)' ':(exclude,top,attr:linguist-generated=true)'`. A changed lockfile (the same names with `:(glob,top)` and `--name-only`) adds the security-reviewer, which gets a diff of those files. Each reviewer gets `<TB> brief <absolute board path> <ID>` (batch: every ID in the batch), the diff command `git diff <work_branch>...<task_branch> -- <pathspecs>`, the worktree path for full files, and its lens or lenses.
4. **Decide:** blocking = critical or high severity with medium or high confidence; have `bosun:verifier` check a doubtful one first. Medium: fix in the same round if cheap, else a follow-up task via `TB add` (OpenSpec plan: a tasks.md id such as `5.1`; TB adds the tasks.md line). Low and nit: record only.
5. **Fix round** (two per task at most, then treat it as `blocked`): send the confirmed blocking findings to the same implementer with SendMessage (`to` = its name) to fix in its worktree, commit and report again. Can't be resumed: spawn a new implementer (worktree) whose prompt starts with "First run `git merge <task_branch>` to pick up the previous attempt", then the findings. Re-run only the reviewers that blocked.
6. **Merge without committing** (you, main checkout, work branch). First check nothing is pending: `git rev-parse -q --verify MERGE_HEAD` fails, `SQUASH_MSG` doesn't exist, `git diff --cached --quiet` passes; otherwise stop, because a squash merge would stack on the leftovers and commit them under this task. Then `git merge --no-ff --no-commit <task_branch>`, or `git merge --squash <task_branch>` if `build.merge` is `squash`. Conflict: `git merge --abort` (after a squash, `git reset --merge`), then the reference, "Conflicts". Shared mode has no branch: reference, "Shared mode".
7. **Integration check** on the merged tree: the fast checks (lint or typecheck, tests near the change). Red: undo the merge (`git merge --abort`, or `git reset --merge` after a squash) and send the task back (`TB set <board> <ID> --status pending --note "<failure>"`).
8. **Record and commit:** `TB set <board> <ID> --status done --summary "<one line>"` (OpenSpec plan: this ticks tasks.md; `git add -- <tasks.md path>` so the tick lands in the same commit, *local: skip the add*). Then `git commit -m "bosun(<ID>): <title>"` and `TB set <board> <ID> --commit <sha>`.
9. **Full suite** about every 5 merges and whenever a schedule wave completes. Red: find the culprit merge, undo it with `git revert -m 1 <merge_sha>` (`git revert <sha>` for a squash commit; never reset), and reopen the task (`TB set <board> <ID> --status pending --note "<failure>"`). The revert unticks tasks.md too; commit if `TB status` still reports drift after `TB sync` (*local*: the revert leaves tasks.md alone, the `TB set` unticks it, nothing to commit).
10. **Clean up:** `git worktree remove <worktree>`, `git branch -d <task_branch>` (after a squash merge git can't tell the branch was merged: `-D` once you've confirmed the squash commit landed). Results are already in `.bosun/plans/<name>/results/`; write `.bosun/plans/<name>/reports/<ID>.md` only for notes of your own (a decision, why you accepted a finding) or for result blocks the hook didn't save.

Report tasks (`kind: report`) aren't merged: mark the task done with a one-line summary (the result is in `.bosun/plans/<name>/results/`) and turn in-scope, actionable findings into tasks with `TB add`. OpenSpec plan: marking it done ticks tasks.md, so commit tasks.md (`git commit -m "bosun(<ID>): <title>" -- <tasks.md path>`; *local: skip*).

## 3. When things go wrong

- No result block: inspect the agent's branch or files yourself. Complete, and its checks pass when you run them: continue at the spot-check (section 2, step 2); otherwise treat it as `partial`.
- `partial` or `failed`, attempts below `max_attempts`: `TB set <board> <ID> --status pending --note "<what to change>"`; the note appears in its next brief. `partial` work worth keeping: put "start with `git merge <task_branch>`" in the note so the next attempt builds on it; remove the old worktree and branch once the retry is merged.
- `needs_input`: ask the user (batch the questions) and keep other tasks moving. Record the answer as a note and set the task to pending. An answer that changes the spec: have `bosun:architect` revise the change (and re-run `TB spec-check`) before the task restarts.
- Attempts exhausted, or `blocked`: `TB set <board> <ID> --status blocked --note "<reason>"`. Tell the user once, with options: clarify, split the task, skip it (`--status skipped` lets dependents proceed and leaves its tasks.md line unticked), or take it over.
- Two tasks in a row failing the same way (broken install, a shared test failing on the work branch): stop dispatching, fix the work branch, then resume.
- `stuck: true`: nothing can start; resolve the blocked tasks with the user.

## 4. Finish

When the board is complete, or only blocked and skipped tasks remain (with `--only`: of the listed tasks; steps 2 and 4 then cover only those and their requirements, and step 7 names the tasks left for a later build):

1. Run the full checks yourself: install, lint, typecheck, test, build. Solo route: skip this step and the next when the run's integration check and gate (section 1, solo step 3) covered every merge since `<base_commit>`; they were these steps (the gate's security-reviewer stands in for the audit).
2. Final review: the `bosun:review` skill on `<base_commit>...HEAD` with lenses correctness and, for an OpenSpec plan, `spec` (every requirement in the change against the code and its tests); with review policy `batch` or `final`, also design and tests (policy `task` already gated every merge). `bosun:security-audit` on the same range only when a security-sensitive task merged without a security-reviewer gate (policy `final` or `off`).
3. Fix critical and high findings through the same pipeline (new tasks via `TB add`).
4. OpenSpec plan: `TB spec-check <board>` clean and every task line in tasks.md ticked. Skipped tasks stay unticked: ask whether to drop them from the change (architect, revise mode) or finish them. With the CLI, `openspec validate <id> --strict --no-interactive` once more, from the OpenSpec directory's parent.
5. No docs task in the plan, and no solo run that updated them: spawn `bosun:docs-writer` for the README and CHANGELOG.
6. Write `.bosun/plans/<name>/SUMMARY.md` from the board, `.bosun/plans/<name>/results/` (several files for one task are retries or reviews; the newest is the latest) and your notes: what was delivered (per requirement for an OpenSpec plan), deviations from the plan, spec gaps the agents reported, decisions made along the way, follow-ups, known issues, how to run it.
7. Tell the user the outcome in a few lines, separating what you verified from what you didn't. Next: `/bosun:ship` pushes and opens the PR (never push yourself); OpenSpec plan: `/bosun:archive <id>` merges the change into `<openspec_dir>/specs/`. Archiving on the work branch before shipping lets the PR carry the updated specs; some teams archive after review instead. A local OpenSpec directory never reaches the PR.
